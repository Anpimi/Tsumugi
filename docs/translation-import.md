# Translation import and editing

Choose **Translations** in the sidebar to open the editor in the main workspace. The list shows each native key, source and selected translation summaries, with selection, human approval and QA presented separately. Search native keys, source text or selected translations across the complete current source scope; results are paged and do not change any confirmed batch selection. Choose an entry to keep its source and editable translation beside the list. **Previous** and **Next** move within the displayed page through the same unsaved-draft protection. Expand reference details for terms, context and revision history. **Save revision** or Ctrl+S saves explicitly; returning from another area keeps the current query, page and entry when the source and target language are unchanged. An editor without an unsaved draft refreshes the current source and translation selection on return; text entered during that refresh is preserved.

For an existing SMAPI language file, choose **Import file** before the folder selection steps below. Import remains separate from ordinary manual editing.

The Translations view works with the current source snapshot of an open project. Import source content and add the target locale to the project first. The first bundled profile supports a single flat SMAPI `i18n/<language>.json` file in a Mod folder. The filename declares a language such as `zh`; you explicitly confirm its mapping to a project target such as `zh-CN`. A file named `default.json`, split translation folders, non-string values, duplicate keys ignoring ASCII case, unsupported encodings, and files over 128 KiB are rejected. The original Mod files are only read.

Choose the Mod folder, select a translation file, check it, and confirm the language mapping. Starting the import saves a fixed copy of the complete file and an execution task. Extraction and matching may take time for a large file. The Tasks view retains the attempt and its recovery actions; it can reopen the translation preview after closing the workbench or the application. Changing or deleting the original file after capture does not change that saved attempt.

The preview compares native keys with the current source snapshot, ignoring ASCII case. Equal text or similar filenames do not establish a match. It shows the imported text, source text, current selection, file evidence, and counts for unique, unmatched, ambiguous, conflicting, and changed-source entries. Unmatched or ambiguous entries remain in the saved task. If the source changes after capture, start another import against the new snapshot. An incomplete or invalid task cannot be applied; inspect its recovery options in Tasks.

**Apply unique matches** creates candidates by default and never replaces an existing selection. You can choose to select those candidates only where no translation is selected. Each entry commits separately, so the progress and summary distinguish committed, conflicted, and uncertain actions. Check an uncertain action's receipt before retrying the same action. For one entry, use the row actions to add a candidate, select an unselected translation, or explicitly replace the current selection after comparing the texts. The write checks the latest source and selection again.

The editor lists source keys and the revision history for one unit and target locale. Saving creates a new immutable manual revision and selects it; empty text is valid. You can select an earlier revision without deleting newer revisions. Imported revisions retain their file, native key, and execution provenance. If a save response is uncertain, retry the same action; a conflicting selection requires comparing refreshed history. Text typed while an earlier save is pending remains a separate unsaved draft. Closing or switching projects with an unsaved draft offers Save and continue, Keep editing, and Discard. An uncertain save must be retried before leaving.

Creating or selecting a translation does not approve it, run QA, build a Mod, or publish anything. Use Review and QA for explicit decisions and current checks, then Build and export for local SMAPI language files. Project data, including saved imports and revision history, stays in the project's SQLite database. See the [README](../README.md#development) for the current database schema and supported upgrades; unsupported schema versions are left untouched.
