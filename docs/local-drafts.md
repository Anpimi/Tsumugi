# Local draft journal

The desktop workspace uses a local journal for unconfirmed translation, conversation, resource and source-maintenance input. Its editor keeps translation input by project, entry, and language, while resource and source-maintenance input are kept by project. The recovery panel lists drafts and requests whose results still need checking. Translation draft recovery after closing and reopening a project has been observed in a native macOS build; recovery after quitting and restarting the whole app has not yet been verified. Conversation, resource and source-maintenance draft recovery have not yet been verified in a native build.

## What is stored

The journal keeps one translation head per project, source entry, and target language. A head can contain draft text, its edit sequence, the original source and translation basis, and a translation-memory reference when one has been placed in the draft. It distinguishes an absent selected translation from a selected empty string. A merge draft also keeps its saved comparison, the contributing revision identities, and the comparison basis. When a save, revision selection, or merge has an uncertain result, the head can also retain the original request and the sequence submitted with it, including its reuse reference. It does not retain session tokens or grants.

The Host stores the journal as `drafts/drafts.sqlite3` under the application data directory, separate from the project folder. Its format version is 17; it does not change the project database schema. This build can read valid formats 1 through 16 as well as format 17. Reads and lists do not upgrade earlier journals. The first successful write upgrades the journal in the same transaction, preserving existing drafts, pending requests, format-12 source corrections and notification-stop input, format-8 knowledge proposal edits, format-7 control requests, and cleared markers. Rejected writes keep the earlier format. An interrupted upgrade leaves the complete original journal or a complete format-17 journal. Builds that only support earlier formats reject format 17 without resetting it. The journal uses SQLite `DELETE` journaling and `FULL` synchronization. A missing journal is not created by a read or list. Opening an existing journal for reading may let SQLite recover an interrupted transaction, but does not add or remove draft records. On Unix, newly created draft directories and database files use owner-only permissions.

Conversation input uses separate typed heads in the same journal. Each proposal can have one unfinished local edit containing its base revision and content, including knowledge proposal entries, summary and questions. The summary, an individual question, or the entry selection can be empty while editing; saving a formal revision applies Core validation. Message input has its own edit sequence, so saving one kind of input does not clear newer input of the other kind. Before creating a thread or appending a message, the original request is saved locally without a session token; the pending request is resolved only after its exact receipt is confirmed. It can also retain the complete original planning, proposal capture, proposal revision, work-plan confirmation, start, and control requests. Start records include the conversation and expected attempt identity; continuation records retain the full Host confirmation fields and nullable expiry. None contains a session token. These records are checked against their original receipts; they do not restore captures, execution permission, or model requests. A missing planning or work-plan confirmation receipt remains blocked and is not replayed. An unresolved work-plan confirmation cannot be cleared in the conversation panel; a new conversation can be used for other work while the original request remains available for checking. The primary pending request continues to govern ordinary conversation mutations. Separately, the same head can retain up to 32 pause, stop, or takeover requests, even while the primary request is unresolved or in flight. These control requests contain no consent. Each must be durably acknowledged by the journal before dispatch; a failed or unconfirmed journal write blocks dispatch. Normal saves retain all pending requests, and resolving one request preserves the others and newer input. A format-6 control request in the primary slot remains readable and can be checked. See [running a linked plan](work-plans.md#running-a-linked-plan-in-a-conversation) for checking and explicit same-request retries; recovery does not restore consent or automatically start work.

For each plan, the conversation head can also retain separate drafts for guidance to a member and a discussion post, including the selected member or entry, text, and any reply target. Each draft has its own edit sequence. Before sending guidance or publishing a discussion, the complete original request must be saved locally; the journal stores no session token, consent, or active runtime permission. A newer edit can be kept while a request is unresolved. A recorded result clears only the submitted text if it has not since changed, preserving newer input and the other draft. Proof that the original request was permanently fenced clears the request but keeps the input. A missing receipt alone does not prove that the request did not take effect; settlement requires the original Core receipt or proof that its lease generation has permanently advanced.

After reopening, saved input and original requests can be read and checked; they do not restore permission to send a new request or automatically resend one. Guidance and discussion show the actual member, role, model, entry and text before an explicit send or publication. A saved message does not mean the member has read it, and sending it does not wake an idle member or start a new task.

Resource drafts and original pending requests share one project-level journal head, including terminology, context, corrections, source facts and knowledge review. A pending request must be saved before it is sent. Reopening reads the saved input without automatically checking receipts, sending again or restoring permission. Check an uncertain action against its original request; a missing record alone does not prove it was not submitted. Knowledge adoption must be compared again and a broader scope confirmed again after reopening; a previously submitted request retains its original comparison and confirmation for checking.

If another window changed the resource draft, compare the saved and local input and copy what you need. A saved head can be explicitly applied only when pending requests agree or both sides have none; different uncertain requests must not overwrite each other. A resource file picker has no recoverable original request: an uncertain picker result remains visible as a warning, and reopening does not open another file dialog automatically.

Source-maintenance input uses a project-level head in this same journal. It retains human mapping choices and reasons, filters and positions, immutable source references, and the exact pending capture, producer start, checker preparation, checker start, checker finish, adoption or entry-match correction request. A separate slot retains an original notification-stop request. Session tokens, native handles, transient preview pages, and active execution permission are not stored. Historical grant and activation fields in an original request serve only to identify that request. Restoring them does not renew permission.

Capture and checker preparation are transient Host operations. Their original references may read an exact cached result in the same live Host session; after that preparation is lost, the app requires selection or preparation again. Losing a transient preparation does not prove a producer start or adoption failed. Checking a durable action uses its original execution or adoption record; missing records remain unresolved. A recorded checker finish remains readable after another checker replaces the current proof. Pure observations do not reconcile or replay work. During the original in-flight action, an exact successful record can finish its acknowledgement recovery within the same reservation. Reopening only restores input; it does not automatically check or settle requests. Settlement verifies the original result before resolving its journal slot and preserves newer mapping input.

A producer or checker start retains its original task and execution generation with its request. Explicitly cancelling an uncertain start first checks the saved draft version and exact pending request, then closes that request's admission through the existing grant store. A late authorization cannot reopen it. An already recorded start remains a recorded task; cancelling the startup request does not stop that task. A new start needs a fresh input review and confirmation. A missing record or an expired deadline alone never proves that startup failed. A notification-stop request likewise needs its own receipt, or proof that another stop permanently closed the same notification. Ending the local stop wait also requires its callbacks to have finished.

After reopening, an already executed checker result can be checked and explicitly recorded from its original saved input and output. This does not run the checker again or restore its permission. Cancellation, revoked authorization, changed results and concurrent project changes still block recording. A persisted cancellation or revoked grant can prove an unpublished request is permanently closed; a previously published result still wins before that check. If another check is already current, recording the earlier result preserves that current check and adds only the earlier result's verified history.

Entry-match corrections keep their input in this same Source head. A read-only comparison and validation run before the exact correction request is saved and submitted. A newer reason or decision stays separate from the submitted request. Reopening restores that input without checking, applying or cancelling the correction. A receipt check can recover a recorded result; an absent receipt only permits an explicit retry of the same original request. Explicit cancellation first checks the journal version and original request, then permanently closes that request if it has not been recorded. A recorded result is retained. Neither path transfers a translation or approval. Format-11 Source heads retain their original payload bytes when the journal upgrades; only an explicit edit changes that head.

Each head has a revision used to reject stale writes and clears. A writer identifier distinguishes editing instances; retrying an identical write from the same writer returns the existing head. Clearing an absent head leaves a marker so an older write cannot bring it back. A head with an unresolved primary or control request cannot be cleared directly. Listing scans these markers as well as drafts, so an empty page can still have a continuation; enumeration ends only when `next` is null.

Batch candidate adoption uses these same heads and writer checks. It preserves existing drafts, protected entries, and non-AI selected translations. The selected entries and excluded members stay fixed as filters change. If a journal write cannot be confirmed, the batch pauses with its input retained; retry that draft write before continuing the entries that have not started. Adopting candidates into drafts does not confirm project translations.

## Limits and recovery

A translation head is limited to 256 KiB. A conversation or resource head is limited to 4 MiB plus 256 KiB so it can retain its original requests. A source-maintenance head is limited to 8 MiB plus 256 KiB to retain an original request alongside newer mapping input. Oversized records are rejected rather than truncated. The journal limits the combined encoded heads to 32 MiB per project and 128 MiB overall, and to 16,384 heads per project and 65,536 overall. Cleared-head markers count toward the head limits. These are journal limits, not guarantees about the database file's total size. The journal does not automatically discard unconfirmed input to reclaim space. A full, unavailable, damaged, or unsupported journal returns an error; unknown formats and damaged files are retained rather than reset. Upgrades preserve existing drafts, unresolved requests, cleared-head markers, and their revisions. Conversation, resource and source-maintenance heads share the same total limits and writer, edit-sequence, revision, and cleared-head protections; unresolved requests cannot be discarded as ordinary cleared drafts. Other unsupported formats are left intact.

The journal belongs to the app data profile, not the project folder. Moving or copying a project does not move its drafts. Deleting app data removes the journal; switching profiles looks in the new profile's app data. Reinstallation only finds the journal if the same app data remains available; preservation depends on the platform and how the app was removed. Keep the database and any accompanying SQLite journal intact when preserving a damaged or interrupted store.

Reading a draft returns its saved basis and a later observation of the current project basis, or reports that the source entry or target language is unavailable. The editor checks the basis before confirming recovered input. Recovery can provide text for copying, but an arbitrary-path recovery export is not implemented. An unresolved save, selection, or merge must be checked against its original request; reading a draft does not retry the request or restore its authorization. Confirming a translation uses the existing manual revision, selection, or merge and protection rules. A merge confirmation retains its original contributing revisions; it is never retried as an ordinary text save. If newer input arrives while a merge is being confirmed, that input and its sources stay in the draft. Recheck the merge sources before confirming the newer text. The journal itself does not create a translation revision, review, QA result, or model request.


Team recovery in a conversation keeps unfinished member settings, stable tool handles, selected work, instructions, discussion references and prior-work references in the same head. Incomplete fields are allowed locally; preparation still applies the original domain checks. The complete preparation request is acknowledged locally before dispatch. A confirmed authorization may be appended once to that same pending request and is also acknowledged before dispatch; the original preparation remains intact. A recorded authorization can be retained for checking, but does not restore a ready-to-start permission after reopening. Starting uses the original plan-start request and expected attempt identity.

A preparation response can be lost before its preview digest is known. The original preparation identity and full request can still stop its exact Host slot and wait for accepted callbacks to finish. Not finding a slot or seeing it closed does not prove permanent absence. Clearing that pending request requires a strictly advanced original lease generation and drained callbacks. An uncertain authorization is checked against the exact original preparation and authorization; only its verified receipt or a permanent generation fence can settle it. Takeover and stop remain separate explicit plan controls. Editing newer input, hiding a view or reopening does not resend preparations, confirmations or model requests.

Member-question answers use the conversation's existing journal head. Unfinished text, a selected option and a closing reason can coexist without submitting a response. The full original question and response request are acknowledged locally before dispatch. A recorded answer clears only the submitted input version; newer text stays available. Reopening checks the same request and never sends it automatically. If another response has already closed that exact question, checking ends the pending request and keeps unsent input. Stopping a plan does not settle an uncertain answer. Answering records a local human response in the project; it neither starts member work nor changes the plan's sharing or budget permissions.

Context experiments have a project-level head in the same journal, with the same quota and writer checks. It keeps unfinished candidate settings, calibration and holdout choices, separate judgment input, selected immutable records and the complete original request without session tokens. A request is acknowledged locally before dispatch; later input remains separate from that request and survives its receipt. Reopening restores input and pending requests, not prepared execution, checker grants or consent. Reads do not retry or settle work. Checking uses the exact original record; an uncertain start or check can be closed only when its original owner confirms that it can no longer dispatch unrecorded work. Closing does not replace a recorded result or cancel an already started evaluation. An initial draft read failure keeps the stored head intact and permits leaving when no new input has been created.

Glossary proposal edits keep the original capture, entry, language and current-term revision in the resource journal. Adopting an edited target uses the same original decision request and receipt. A delayed acknowledgement clears only the submitted edit; newer input remains. A changed term requires comparing the retained input against the new current term before explicitly rebasing it. Reopening never adopts or resends an uncertain decision.

Preparing an Agent repair from a recorded team finding appends the exact finding, current source and translation to retained conversation input and selects only that entry and language. It clears old planning consent and message choices. The user must save the new message and review the original materials, budget and consent before any model request. Unconfirmed actions or failed local writes remain in their original owners.
