# Tsumugi

**紡ぎ**

面向持续演进内容的可扩展本地化工作台，原生支持 AI 与 Agent 工作流。

Tsumugi 将源内容、翻译、术语、上下文、审阅、验证、发布与后续维护放在同一个项目中管理。它关注的不只是“如何翻译”，也包括内容更新之后，哪些工作仍然有效、哪些需要重新处理，以及这些判断从何而来。

## 概览

本地化通常不是一次性的工作。

源内容会更新，翻译会被修改，术语和上下文会发生变化，已经完成的工作也不一定始终适用于新的版本。

Tsumugi 将这些变化视为项目生命周期的一部分：

```text
导入
  → 翻译
  → 审阅
  → 验证
  → 构建
  → 发布
  → 更新
```

当新的上游内容被导入时，已有成果不会默认失效或被丢弃。

Tsumugi 会根据内容身份、版本沿袭和相关依赖判断哪些工作仍然适用，哪些需要重新验证、翻译或审阅，并保留足够的历史信息解释这些变化。

## 项目模型

Project 是 Tsumugi 中长期存在的本地化工作单元。

一个项目可以包含：

- 源内容快照与修订
- 本地化单元及其来源位置
- 目标语言与翻译修订
- 术语与上下文
- 审阅决策
- QA 与验证结果
- 工作项与执行任务
- Release 与交付记录

内容身份与文本值和物理位置相互独立。

相同文本不一定代表相同内容；内容即使在新版本中移动或发生变化，也可能仍然延续同一个逻辑身份。

翻译、人工审阅、当前适用性和验证状态同样彼此独立。

一个翻译可以已经存在但尚未经过审阅；一个曾经通过审阅的翻译，也可能因为相关源内容、上下文或约束发生变化而需要重新确认。修改翻译不会自动继承旧版本的批准结果。

## 持续维护

上游更新是正常工作流的一部分，而不是一个独立的迁移过程。

导入新的源版本后，Tsumugi 可以区分：

- 仍然适用的工作
- 需要重新验证的工作
- 需要重新翻译或人工确认的工作
- 无法自动判断的变化

内容的新增、删除、修改、移动、拆分、合并以及无法确定的对应关系，都可以作为版本沿袭的一部分被记录。

已经不再适用于当前版本的翻译和决策仍然保留在项目历史中。

更新因此建立在已有成果之上，而不是每次重新开始。

## Native AI 与 Agent

AI 是 Tsumugi 的原生能力，而不是附加在编辑器上的独立功能。

常规任务可以直接调用模型；需要调查、分析或多个步骤协同完成的任务，则可以通过内置的 Agent Runtime 执行。

一个 Agent Task 可以获得明确限定的：

- 任务目标
- 项目上下文
- 可用工具
- 执行限制
- 结构化输出要求

适合 Agent 处理的工作包括上下文调查、术语冲突分析、审阅、修复建议以及其他需要结合项目状态进行推理的任务。

Agent 使用的工具具有明确权限。调查类操作通常以只读方式进行；涉及项目修改时，Agent 提交的是结果或变更建议，由 Core 负责验证和采纳。

因此，Agent 不拥有项目状态，也不能绕过正常的翻译、审阅和发布规则。

AI 产生的翻译候选、审阅信号、上下文发现或其他结果，与人工工作使用同一套项目模型和历史机制。

Tsumugi 原生支持 AI，但并不依赖 AI 才能工作。手动翻译、审阅和维护仍然是完整支持的工作方式。

## 执行与结果采纳

耗时的提取、翻译、索引、QA、比较和构建操作使用统一的任务执行机制。

任务可以具有进度、取消、重试、恢复和历史记录，并基于确定的输入版本运行。

执行结果不会因为任务成功返回就直接覆盖当前项目状态。

在结果被采纳之前，Core 会检查相关前提是否仍然成立。

例如，当 AI 或 Agent 正在处理某条翻译时，如果用户已经手动修改了它，稍后返回的结果可以继续作为候选保存，但不会覆盖更新后的版本。

## 扩展模型

Tsumugi 将本地化语义与领域知识分开。

Core 负责项目状态、生命周期规则、权威决策，以及其他能力参与项目时必须遵守的边界。

扩展通过明确的 Capability Contract 提供能力。

一个扩展可以提供多个相关能力，也可以只提供数据或可复用资源。扩展产生的结果需要返回 Core，并通过正常的验证和采纳流程进入项目。

扩展不会直接拥有项目模型，也不会通过直接访问内部存储来改变项目状态。

公开扩展契约与内部实现保持分离。可执行扩展通过与语言无关的边界通信，不要求与 Core 使用相同的实现语言。

这样可以在增加新领域和新能力的同时，继续使用同一套项目语义和生命周期。

## 构建与发布

编辑、构建、发布和交付是不同的操作。

一次 Release 基于固定的项目输入和经过验证的构建产物产生：

```text
项目状态
    ↓
固定 Release 输入
    ↓
构建前验证
    ↓
构建
    ↓
构建后验证
    ↓
记录 Release
    ↓
导出 / 安装 / 发布
```

翻译在编辑器中通过检查，并不意味着最终产物一定有效。

Tsumugi 因此会区分构建前的项目验证和构建后的实际产物验证。

构建失败不会被记录成成功的 Release；而一个已经成功生成的 Release，也不会因为之后的导出、安装或外部发布失败而消失。

## 架构

当前参考实现采用：

```text
React + TypeScript
        │
      Tauri
        │
    Rust Core
        │
Language-neutral Capability Protocol
        │
Workers / Data Extensions / External Tools
```

桌面界面负责呈现状态和请求操作，但不拥有权威状态转换。

Rust Core 负责项目语义、状态约束、持久化、任务编排、结果采纳与 Release 状态。

可执行的领域能力通常运行在独立 Worker 中，并通过与语言无关的协议与 Core 通信。

Worker 可以使用适合自身领域的实现技术，公开扩展契约不会绑定 Rust ABI。

## 当前状态

Tsumugi 仍处于早期开发阶段。

当前工作主要集中在完整本地化流程所需要的基础设计与实现，包括：

- Project 与语言边界
- 内容身份与版本沿袭
- 翻译与审阅状态
- 术语、上下文与依赖关系
- 影响分析与既有成果复用
- Native AI 与 Agent Runtime
- 执行任务与结果采纳
- QA、构建与 Release
- 扩展边界
- 持久化、历史与恢复

详细 API、存储 Schema、Worker Transport 以及稳定的公开扩展契约仍在设计中。

目前不存在稳定的 Plugin API。
